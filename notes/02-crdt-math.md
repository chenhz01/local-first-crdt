# 本地优先软件 · 技术思维 #2：CRDT 用数学保证收敛的合并

## 两性费曼 · 性一（12 岁也能懂）
- **这是什么**：两个人各搭一半积木，最后一定拼出同一座城堡——因为规则保证谁先谁后都一样。哪里不像：积木搭错了可以拆，数据被覆盖的改动若没留下流水账，就再也找不回来。
- **与我何干**：避险。两台设备同时改、中途断网、消息重复送达，都不会丢改动，也不需要谁来判断谁对。
- **我该怎么办**：两小时内用任一 CRDT 库起一个双标签页示例：两个标签页都离线改同一段文字，恢复连接看是否合并成同一结果，再把同一条更新重复发送几次看结果是否不变。

## 两性费曼 · 性二（同行可验证）
- **机制**：合并操作满足交换律、结合律、幂等律，因此任意顺序、任意重复地应用同一组操作，所有副本必然收敛到同一状态；字符用唯一位置 ID 而非数字下标定位，避免他人插入造成位置漂移。
- **边界数**：三条代数律（交换 / 结合 / 幂等）[一手]；每字符携带唯一 ID 与设备标识带来的体积膨胀 [一手]；首屏 bundle 数 MB（WASM 数据库引擎 + CRDT 库）[一手]；95% 场景可由 last-write-wins 覆盖 [二手]。
- **反例**：若实测出现同一组操作在不同应用顺序下收敛到不同状态，或重复投递改变结果，则该实现的 CRDT 性质不成立；若能在 cloud-first 系统上低成本后补成功，「必须从架构第一天设计」的警告即被推翻。
- **可复现**：见正文「最小下一步动作」——双标签页离线编辑加重复投递，全程不需要服务器，也不需要写一行冲突解决代码。

## 一句话（费曼层）
两个人同时改同一段话，CRDT 就像一套神奇的积木规则：不管谁先谁后、中间隔了多久、来回传了多少遍，最后拼出来的作品一模一样。

## 为什么这条路线被低估
合并冲突在主流叙事里是「后端工程师的脏活」——加锁、版本号、时间戳、最后写赢，凑合能过。CRDT 属于那种「论文里见过、生产里没人敢上」的类别：它牵涉序理论、格结构、因果一致性这类数学名词，劝退指数高；早期实现的元数据膨胀和性能问题又给了保守派现成的拒绝理由。于是形成一个奇怪的均衡：冲突每天都在丢数据，而解法躺在论文里没人捡。但本地优先把这个问题逼到了墙角：设备之间没有中央服务器仲裁，每一次离线编辑都在制造并发，冲突不是异常而是常态。事实是，2026 年生产级框架（Automerge、Yjs、cr-sqlite 等，事实包）已把 CRDT 封装进日常 API，数学被藏进了库函数里。低估不发生在原理层面，而发生在「知道它已经可用」与「还在用加锁硬扛」之间的时间差——多数团队对 CRDT 的认知还停留在几年前的评估备忘录里，而备忘录引用的性能数据早已过期。

## 第一性原理拆解
并发合并的第一性问题是：给定一组乱序到达的操作，系统能否保证所有副本收敛到同一状态？传统方案靠中心节点定夺，本地优先没有这个中心。CRDT 的解法是从数据结构层面让「乱序」失去破坏力：操作满足交换律、幂等律、结合律，任何顺序应用都收敛到同一状态（事实包）。交换律保证先后无关；幂等律保证同一条消息重发十遍结果不变——这对弱网环境下的重复投递是刚需；结合律保证分批合并与逐条合并等价。它不存最终状态而存操作（或特殊结构）；每个字符有唯一位置 ID，插入删除引用 ID 而非数字位置——数字位置会随他人插入而漂移，ID 不会；设备 ID 决定并列插入的确定性排序，于是「谁排在前」不再需要裁判。翻译成大白话：冲突在数据结构设计阶段就被消灭，而不是在运行期处理。这正是它与「锁 + 版本号」路线的高低之分——前者把正确性交给数学，后者把正确性交给运维时的运气。补一个常被混淆的区分：CRDT 有基于操作的与基于状态的两支，事实包表述为「不存最终状态而存操作（或特殊结构）」——前者同步「发生了什么」，后者同步「现在是什么」，两支在工程上都要处理历史压缩与垃圾回收，否则元数据无限膨胀。但对使用者而言分支不重要，重要的是两条性质对所有分支通用：乱序收敛、重复无害。选型时只需问库三个问题：乱序能收敛吗？重复投递会怎样？历史怎么回收？三个答案合格，数学就是可靠的。

## 技术机制与关键事实
- CRDT 核心机制（事实包）：不存最终状态而存操作（或特殊结构）；任何顺序应用都收敛到同一状态。
- 文本协同机制（事实包）：每个字符有唯一位置 ID；插入和删除引用 ID 而非数字位置；设备 ID 决定并列插入的确定性排序——无中央服务器也能解决冲突。
- 生产落地（事实包）：Automerge、Yjs、cr-sqlite（SQLite 内置 CRDT）等框架已进入 2026 生产级生态，CRDT 从库变成数据库内置能力。
- 规模证据（事实包）：Linear、Figma 的生产部署证明百万用户级可行——协同合并不是 Demo 玩具，是经过生产流量检验的工程件。

## 反例与证伪条件
CRDT 不是免费的，证伪点有三。其一，元数据开销：每个字符携带唯一 ID 与设备标识，文本体积显著膨胀，事实包明确把 bundle 体积（WASM 数据库引擎 + CRDT 库 = 首屏数 MB）列进现实约束——数学的正确性是用字节数买的。其二，95% 的应用根本不需要全量 CRDT——last-write-wins 加审计日志即可覆盖（事实包，详见思维件 #8），上 CRDT 是过度设计，是用顶配成本买用不上的保险。其三，CRDT 要从架构第一天设计，不能后补到 cloud-first 系统上（事实包）——retrofit 的成本足以让团队放弃，指望「先上云后改造」的路线被事实包直接否掉。三条叠加的结论：CRDT 是架构决策不是功能选型，想清楚了再上，上就想清楚。

## 对善伦业务的迁移点
小说创作：多设备续写同一章、与编辑来回改稿，是天然 CRDT 场景——改动永远不丢，无需手动解决冲突，改稿历史即审计轨迹，版本回溯变成免费能力。AI 音乐：工程文件的参数轨、版本分支可以用 CRDT 管理，两台机器上未联网的调整自动合并，创作者不需要理解任何同步概念。跨境电商：商品库的多人维护不必上全量文本 CRDT——库存计数、标签集合这类子结构（计数器、集合型 CRDT）才是对症的子集，按需取用而非全家桶。正明 AI 系统的跨设备记忆同步：若确定要做，从第一天按 CRDT 架构设计，别等 cloud-first 成型再补——事实包已经把后补这条路标了红叉。

## 最小下一步动作（≤2 小时）
在本地起一个最小 Yjs 或 Automerge 示例：开两个浏览器标签页模拟两台设备，都离线编辑同一段文本，然后恢复连接，观察合并结果；再故意把同一条更新重复发送几次，确认结果不变。全程不需要服务器，也不需要写一行冲突解决代码——你会亲眼看到「任何顺序收敛到同一状态」是什么意思。
