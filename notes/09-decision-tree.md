# 本地优先软件 · 技术思维 #9：选型决策树

## 两性费曼 · 性一（12 岁也能懂）
- **这是什么**：买东西前先问自己三句话：断网时我还用得上吗？这东西丢了我伤筋动骨吗？我要用它十年吗？三句都答「是」再掏钱。哪里不像：买错东西能退货，架构选错要重写全部数据。
- **与我何干**：省钱。把「要不要」从信仰问题降级成算术问题，就能避免在根本不需要的场景里，白付架构复杂度的账。
- **我该怎么办**：两小时内拿你当前最重要的一个在做项目，按四问（离线关键 / 数据主权 / 十年可读 / 团队余量）逐条答「是」或「否」，写进项目说明文件的第一节，并在文末写下下次复审日期。

## 两性费曼 · 性二（同行可验证）
- **机制**：选型的判据是约束匹配而非技术先进——把网络条件、数据敏感度、生命周期、团队规模四项硬约束与架构成立条件对表：前三问全中且团队有余量则成立，前三问全否则走云 SaaS，中间态取混合。
- **边界数**：四问判据（离线关键 / 数据主权 / 供应商独立 / 团队余量）[一手]；适用域含外勤现场、医疗政务法律、长期保存 [一手]；不适用域含快速原型、纯在线应用、资源有限团队 [一手]；复审周期按季度 [推算]。
- **反例**：若埋点测出的真实网络分布与「离线关键」的假设相反，第一问即判错，结论随之失效；若纯在线应用后来长出外勤模块而架构无法演化，说明「一锤定音」的选型方式不成立。
- **可复现**：见正文「最小下一步动作」——对单个项目按四问打分并写入项目说明；同时用埋点统计真实离线时长占比来校验第一问。

## 一句话（费曼层）
要不要用本地优先，先问三个问题：没网能不能干活？数据是不是命根子？这东西要活十年吗？三个都答「是」再动手，有一个答「否」就缓一缓。

## 为什么这条路线被低估
选型判断天生不容易被重视：它不指向任何新工具，只给出一套判断框架，读起来还像泼冷水。但事实包把适用边界写得相当克制：离线关键（外勤）、数据主权（医疗 / 政务 / 法律）、供应商独立（长期保存）该用；快速原型（Firebase 更快）、纯在线应用、资源有限别碰。这种「明确告诉你别用」的资料反而稀缺，因为多数技术推广只讲收益不讲代价，只递锤子不劝住手——劝人住手的话没人愿意写。决策树的价值：把「要不要」从信仰问题降级为算术问题——这是对前八篇思维件的收敛，也是给行动派的刹车片。装在脑子里的不是一堆项目名，而是一棵会自己生长的树。

## 第一性原理拆解
技术选型的第一性不是「哪个先进」，是「约束匹配」：把产品的硬约束——网络条件、数据敏感度、生命周期、团队规模——列出来，与架构的成立条件对表，匹配则用，不匹配则弃。本地优先的成立条件可以压缩成四问：① 主要场景是否弱网或离线？② 数据主权是否有合规或资产要求？③ 是否需要十年以上的可读性（供应商独立）？④ 团队是否有余量承担从第一天开始的架构设计？四问的答案分布直接指向结论，事实包的判据正是这四问的经验版本：前三问全中且第四问答「是」，本地优先成立；前三问全否，Cloud SaaS，别折腾；中间态，混合架构——身份与同步上云买便利，资产本地保主权。四问之外还有一条元规则：选型结论要按季度复审，因为产品的场景会漂移，今天的纯在线应用明天可能长出外勤模块。还有一个隐藏的第五问：谁是你的用户——用户是自己（一人公司工具），约束全松，本地优先几乎是白送的权利；用户是客户，约束全严，每一条都要过审计；用户是协作者，约束在中间，混合架构是标准答案。善伦的正明 AI 系统是第一类，跨境电商工具是第二类，这条维度常常比前四问更快给出答案——先问服务谁，再问怎么建。

## 技术机制与关键事实
该用（事实包）：
- 离线关键：外勤、现场、差旅——网络最差的时候恰是最需要记数据的时候，转圈不是体验问题是数据丢失问题。
- 数据主权：医疗、政务、法律——数据归属有合规刚需，出事时「数据在别人机房」是致命陈述，法务不过审。
- 供应商独立：长期保存——文档不依赖任何厂商的服务器还活着，十年后文件打得开比功能炫重要。

别碰（事实包）：
- 快速原型：Firebase 更快，先验证需求再谈架构，顺序不能反——原型阶段追求架构正确是昂贵的洁癖。
- 纯在线应用：没有离线场景，本地优先收益为零，成本照付，bundle 体积还拖慢首屏。
- 资源有限：架构要从第一天设计（事实包），小团队没有返工余地，一步错就是全局错，别用架构复杂度赌团队余量。

## 反例与证伪条件
决策树是启发式不是定理，证伪点有三。其一，边界场景误判——「以为离线关键，其实用户永远在有网环境」，过度设计的成本白付；解法是先用埋点测真实网络分布再决策，别凭想象，数据比立场可靠。其二，混合策略被忽略——决策树容易诱导非此即彼，其实 Relay.md 式混合（中心身份加 SSO，文档留本地，事实包）说明「部分本地优先」是合法答案，树干上长的可以是混合枝——多数真实产品长在混合枝上。其三，时变性——今天的纯在线应用明天可能长出离线场景（移动端、外勤模块），选型要留演化余地而非一锤定音，架构判断要按季度复审，把「什么时候重新问这四个问题」写进团队日历。

## 对善伦业务的迁移点
跨境电商：客户资料与报价档案——离线关键（展会、工厂、航班）、数据主权（客户资产是命根子）、长期保存（复购周期以年计），三问全中，本地优先成立，且第四问答「是」——一人公司有余量从第一天设计；店铺运营数据——纯在线加平台托管，别碰，顺着平台规则走，把架构精力留给生产资料层。AI 音乐：工程文件本地天然成立，这是行业物理形态；元数据同步看团队规模，一人公司阶段别过度设计，等真有协作需求再按树走一遍。小说创作：书稿是十年期资产，本地 markdown 主副本（Obsidian 模式，事实包列为代表产品）成立；协作改稿等真有编辑协作再上，顺序依然是先需求后架构。正明 AI 系统：记忆库与知识库按数据主权问句设计本地优先；推理调用与备份同步留在云层——这棵树在一个人身上也可以长混合枝，而且应该长。

## 最小下一步动作（≤2 小时）
拿你当前最重要的一个在做项目，按四问打分（是 / 否），把答案写进项目 README 的第一节，并在文末写下「下次复审日期」。如果四问有任意一问答「是」而你现在没有本地副本，这就是本周要补的洞；如果四问全「否」，把本地优先从你的技术清单上划掉——省下的架构预算，是这条决策树给「否」派的回报，泼冷水也是服务。
