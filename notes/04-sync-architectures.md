# 本地优先软件 · 技术思维 #4：同步架构三型

## 两性费曼 · 性一（12 岁也能懂）
- **这是什么**：三个同学传纸条——全都交给班长转交、两人直接递、或者平时交班长、班长不在就自己递。哪里不像：纸条丢了可以重写一遍，数据乱了可能永远拼不回原样。
- **与我何干**：省钱。单人单设备根本不需要任何同步架构；选对拓扑省掉的是服务器运维与直连穿透调试这两笔长期开支，小团队通常只养得起一种形状。
- **我该怎么办**：两小时内在纸上画出你产品的数据流，给每条边标色（蓝 = 必须经服务器、绿 = 可直连、黄 = 需要兜底），统计三色占比，最高的那一色就是你的架构类型。

## 两性费曼 · 性二（同行可验证）
- **机制**：同步拓扑由三个约束穷举得出——网络拓扑（设备能否直连）、信任模型（谁有资格当中转）、可用性要求（服务端挂了还能不能用）；不接受第三方信任只剩 P2P，要求权限可审计则回到客户端-服务器，两者都要即为混合。
- **边界数**：三型分类（客户端-服务器 / P2P / 混合）[一手]；混合型代码量约为单架构的 1.5 倍以上 [推算]；百万用户级客户端-服务器生产案例（Linear、Figma）[二手]。
- **反例**：若单人单设备产品上任何一型同步架构都能带来净收益，说明「三型穷举」漏掉了「不同步」这个更优解；若 P2P 在两台设备永远错峰在线时仍能保证数据可达，「在线率即可用性」的约束失效。
- **可复现**：见正文「最小下一步动作」——对数据流做三色标注并统计占比；更进一步，直接断开服务端，观察本地副本能否继续写入并在恢复后正确合并。

## 一句话（费曼层）
设备之间传数据只有三条路：经一个中转站、两点直接拉手、或者平时走中转站、直连断了就自己兜底。

## 为什么这条路线被低估
「同步」在主流叙事里约等于「调 API」——客户端发请求，服务端返回，链路单向且清晰，同步的拓扑可能性从未进入过讨论范围。本地优先把同步变成了双向、多副本、可离线的问题，此时「怎么传」本身成了一个需要分类的架构维度。低估的原因在于：多数团队把传输层当作实现细节，直到 P2P 的 NAT 穿透失败、或者服务端同步的可用性纠纷爆雷，才发现架构选型早就埋好了因果。事实包给出的三型分类（客户端-服务器 / P2P / 混合）是把这个问题一次性摆上台面的最小框架，值得每个做本地优先的团队过一遍——它的价值不在新颖，在穷举：看完三型，你不会再发明第四种。

## 第一性原理拆解
同步 = 冲突解决 + 数据传输。冲突解决归 CRDT（思维件 #2），数据传输的选择空间由三个约束夹出：网络拓扑（设备能否直连）、信任模型（谁有资格当中转）、可用性要求（服务端挂了还能不能用）。把这三个约束的全部合法组合列出来，只剩三型。这不是设计模式手册上的分类游戏，是物理与信任约束的穷举结果：不接受任何第三方信任，就只剩 P2P；要求权限清晰可审计，就回到客户端-服务器；两者都要，就得到混合。三型没有贵贱，只有与约束的匹配度。选择程序因此是机械的：先写信任模型（谁能看什么），再写可用性要求（服务端宕机时的降级策略），最后看网络现实（用户设备分布）——三张答卷交完，架构自己浮出水面。再补一个常被忽略的维度：同步的拓扑方向性。客户端-服务器天然是星型拓扑，数据汇聚到服务器再分发，服务器既是路由也是见证者；P2P 是网状拓扑，每条边都是双向契约，没有见证者，纠纷只能靠数据自己（CRDT 的数学）裁决；混合是星型加 mesh 的叠加态，平时星型保简单，断网时 mesh 保连续。拓扑决定运维形状：星型的运维压力集中在服务器，mesh 的运维压力分散在每台设备——一人公司的运维预算，通常只够养一种形状。

## 技术机制与关键事实
- 客户端-服务器（事实包）：服务器为权威中转，代表模式 Linear / Notion。优点是实现简单、权限清晰、审计容易；缺点是服务端是单点，也是必须信任的一方——「本地优先」成色取决于本地副本有多完整。
- P2P（事实包）：设备直连，代表产品 Anytype。优点是无服务器依赖、抗单点故障、无审查；缺点是 NAT 穿透、在线率、设备发现都是工程硬骨头，设备错峰在线就等于数据不可达。
- 混合（事实包）：服务器便利层 + P2P 兜底，被判定为「最实用」。服务器在线走服务器（省电、简单），服务端不可达时设备直连自救（保可用）。
- 可行性证据（事实包）：Linear、Figma 的生产部署证明百万用户级可行——客户端-服务器路线一样能撑起生产规模，且不丢本地优先的即时性；说明三型之争是约束匹配，不是规模竞赛。

## 反例与证伪条件
三型各有死法。纯客户端-服务器：服务端宕机即全站停摆，且「本地优先」成色不足，退化成「离线缓存优先」——数据主副本仍在别人手里，同步层只是缓存层。纯 P2P：设备不在线时数据不可达，移动端后台限制与电量消耗（事实包列出现实约束）会教做人，两台设备永远错峰在线就等于永不同步；另外 P2P 的权限管理没有现成范式，思维件 #7 的「认证与无中心权限管理增加摩擦」在此兑现。混合：复杂度翻倍，两套传输路径都要测试、都要处理冲突合并，小团队容易两面不讨好，代码量约为单架构的一点五倍以上（估算）。如果产品只有单人单设备（比如纯单人工具），三型都是过度设计，一个文件加版本控制就够。

## 对善伦业务的迁移点
跨境电商：客户资料、订单走客户端-服务器（团队协作加权限清晰，Linear / Notion 模式已被生产验证），服务器的角色是便利层不是真理层——本地数据库保留完整副本，服务端挂了内网照常开单；展会现场的设备间传图、传视频素材走 P2P；出差弱网环境下混合架构兜底。AI 音乐：创作者通常单设备或双设备，P2P 直连足够，无需自建同步服务，省下的运维就是一人的产能。小说创作：手稿同步用混合型——平时经云端便利层，云端不可达时两台电脑直连兜底，交稿日前夜断网也不慌。正明 AI 系统的记忆层：单人使用，P2P 或「本地存储加定期导出备份」即可，不必引入服务器，把复杂度预算留给真正需要的地方。

## 最小下一步动作（≤2 小时）
在画布上给你产品的数据流图标颜色：蓝色 = 必须经服务器（含权限、协作需求），绿色 = 可 P2P 直连，黄色 = 需要混合兜底。统计三色流量占比，你的架构类型就是比例最高的那一色；没有任何一色超过一半，说明你该先想清楚产品到底服务谁、数据到底归谁。
