# 本地优先软件 · 技术思维 #1：loading 转圈是架构失败

## 两性费曼 · 性一（12 岁也能懂）
- **这是什么**：像你写作业时，本子不在你桌上，而在隔壁楼里——你每写一个字都得派人跑一趟问「这么写行吗」。哪里不像：隔壁楼不会塌，网络会断，断了你一个字也写不了。
- **与我何干**：避险。写入不依赖对方服务器是否在线，服务停摆、订阅涨价时你仍能继续干活，不必把工作进度押在别人的机房上。
- **我该怎么办**：今天花半小时，用浏览器开发者面板测一次云端保存的完整往返耗时，再在本地磁盘写一个同等大小的文件并计时，把两个数字记进笔记。

## 两性费曼 · 性二（同行可验证）
- **机制**：延迟由数据主副本的物理位置决定——本地写入走内存与磁盘，微秒到毫秒级结束；云端写入被光速上限、TCP 协议栈、服务端排队共同约束，量级差一个数量级以上。
- **边界数**：本地写 <10ms [一手]；云端 API 往返 200ms+ [一手]；界面反馈舒适线约 100ms [推算]；每天保存 20 次时纯云端累计等待 4 秒以上 [推算]。
- **反例**：若出现全球范围稳定 <10ms 的云端往返，本地主副本的延迟优势归零，本条结论失效；社交信息流、全球库存、千人同屏这类需要全局一致的场景本条不适用（详见正文证伪节）。
- **可复现**：见正文「最小下一步动作」——同一份文件分别在本地磁盘与云端工具各保存一次，用计时数据直接对比。

## 一句话（费曼层）
你屏幕上转圈圈，是因为你刚写的东西不在自己电脑里，而在别人机房里——你的电脑得先寄一趟信过去问一声，才能把字显示出来。

## 为什么这条路线被低估
过去十五年，工程讨论的默认前提是「服务端是权威」。招聘要求云经验，认证考云架构，技术大会默认这一前提，转圈被当成互联网产品的胎记，没人觉得需要解释。移动互联网又加深了这层麻醉：弱网、loading、下拉刷新，用户被训练成接受「等待是数字生活的默认背景音」。工程师的聪明才智几乎全部花在「让云端更快」上：CDN、边缘节点、连接池、缓存、预热。这些都是对的方向，但回答的是错的问题——真正该问的是：为什么敲一次键盘要出一趟远门？延迟对比是硬的（事实包数据）：本地写 <10ms，云端 API 往返 200ms+，差了一个数量级以上。按这两个数字推算：一个每天保存二十次的文档，纯本地写入累计不到一秒，纯云端保存累计等待四秒以上——每天、每个用户、每个会话。转圈不是技术限制，是架构把数据主副本放错了地方之后，UI 层被迫打的补丁。一个被主流叙事定义为「正常」的体验，恰恰是架构失败的显影。直到 2026 年，首届 Local-First Conference 举行、FOSDEM 2026 为 local-first 开辟 8 小时专场（事实包），这个被晾了七年的问题才开始拥有自己的会场。

## 第一性原理拆解
把「编辑一个文档」拆到不能再拆：读、改、写。这三步的物理路径由一个问题决定——数据的主副本住在哪里。住在本地：读走内存，写走磁盘，微秒到毫秒级结束，UI 线程根本不参与等待。住在云端：每一次写都是一次网络往返，延迟被光速上限、TCP 协议栈、服务端排队共同锁死，UI 线程只能挂着转圈，用户的时间被切成无数个 200ms 的碎片。Ink & Switch 2019 年论文《Local-first software: You own your data, in spite of the cloud》（Martin Kleppmann 等，事实包）把结论写成七准则，顺序摆明了：即时响应排第一，其后才是多设备同步、离线可用、实时协作、数据耐久、安全隐私（端到端加密）、用户控制。注意这不是改良清单而是依赖关系——没有即时响应，其余准则全是空中楼阁：一个每次按键都卡顿的工具，谈什么离线协作都是奢侈。本地优先的本质是重新回答第一问：本地设备是 source of truth，云端降级为同步、备份、协作的便利层。转圈这个 UI 症状，只是这个架构选择在屏幕上的显影。再往下推一层：延迟是一种预算。界面反馈的舒适线大约在 100ms 以内（交互设计常识，估算值），本地写入 <10ms，意味着每次保存连一成预算都花不掉，UI 可以毫无顾忌地即时呈现；云端 200ms+ 的往返一次就超支数倍，于是产品经理发明了转圈、骨架屏、乐观更新这一整套补丁技术——乐观更新尤其讽刺：它的本质是「先假装本地优先，等服务器追认」，而本地优先只是把假装变成了默认。

## 技术机制与关键事实
- 延迟量级（事实包）：本地写 <10ms；云端 API 往返 200ms+。
- 七准则来源（事实包）：Ink & Switch 2019 论文，Martin Kleppmann 等——即时响应、多设备同步、离线可用、实时协作、数据耐久、安全隐私（端到端加密）、用户控制。七条可归为三组：体验组（即时响应、离线可用）、协作组（多设备同步、实时协作）、资产组（数据耐久、安全隐私、用户控制）。
- 2026 成熟标志（事实包）：首届 Local-First Conference 举行；FOSDEM 2026 为 local-first 开辟 8 小时专场。
- 产品佐证（事实包）：Obsidian 以本地 markdown 为主副本，日常写作零转圈，是该思路的代表产品；Linear、Figma 的生产部署证明该思路在百万用户级产品上同样成立。

## 反例与证伪条件
两种证据能证明这条思路错。第一，若出现全球范围稳定 <10ms 的云端往返（物理层或协议层突破），本地主副本的延迟优势归零，转圈退回纯优化问题，届时「转圈是架构失败」的指控失效。第二，事实包明确列出现实约束：社交信息流、全球库存、千人同屏游戏这类场景仍必须中心化云——全局一致与中心编排不可替代，本地优先在这些场景会让位。换言之，这条思维件的适用范围，止步于全局一致刚需出现的地方；在边界之内，转圈依然是架构失败的显影，而不是命运的妥协。

## 对善伦业务的迁移点
跨境电商：展会现场、供应商工厂、跨洋航班，网络恰是最差的，而商品草稿、客户跟进、报价记录恰是最需要随手写的——本地主副本让这些场景零转圈，回到酒店连上 Wi-Fi 自动同步，现场不错过、事后不补录。小说创作：章节稿以本地为主副本，写作工具停服、订阅涨价、服务器故障都拿你没辙，文件永远打得开——对以十年为单位经营的 IP，这是底线保障。AI 音乐：工程文件本地保存本是行业惯例，把元数据与版本历史也纳入本地优先架构，是顺路的事。正明 AI 系统的记忆检索同理：查自己的知识库不该有网络往返，本地引擎的毫秒级响应才是「幕僚长」该有的反应速度。

## 最小下一步动作（≤2 小时）
打开你最常用的云端笔记或文档工具，用浏览器开发者面板的 Network 计时一次完整保存往返；再在本地磁盘写入同等大小文件并计时。把两个数字记进今天的笔记，再乘以你每天保存的次数，算出每天纯等待的秒数——这个数量级差距就是本条思维件的全部体感。
